# 主要技术挑战

## Fabric 生成与 Geth 生成之间最大的差异

`newTranslator` 同时面向 **Hyperledger Fabric** 与 **Geth/Ethereum** 生成执行代码，但这两类目标平台的执行模型差异很大，所以最大的技术挑战并不是“换一套模板”，而是要把同一份 BPMN/DMN 语义稳定地映射到两种完全不同的链上运行时。

### 1. 最大差异：执行与身份模型不同

- **Fabric 生成**
  - 目标产物是 **Go 链码**。
  - 运行环境是 Hyperledger Fabric 的链码容器。
  - 身份体系以 `MSP/X.509` 为核心，参与方天然带有组织属性。
  - 合约调用通常可依赖链码上下文、通道、背书与链码间调用。

- **Geth 生成**
  - 目标产物是 **Solidity 智能合约**。
  - 运行环境是 EVM。
  - 身份体系以 `address` 为核心，权限控制需要在合约里显式建模。
  - 所有状态变更、流程推进、外部调用都必须受 EVM 语义、gas 和 ABI 限制。

这意味着：**同一个“参与者发送消息并触发下一步”的业务语义，在 Fabric 和 Geth 上的实现基础并不一样**。Fabric 更像“联盟链业务组件编排”，Geth 更像“受限虚拟机里的状态机实现”。

### 2. 为什么这是最大挑战

#### 2.1 参与者身份映射完全不同

- Fabric 中，参与者可以自然映射为 `MSP + X.509 + attributes`。
- Geth 中，参与者主要映射为链上地址和合约内权限表。
- 因此，同一份 DSL 里的 `participant`，在两端不能直接复用同一种运行时假设。

#### 2.2 消息与流程推进机制不同

- Fabric 链码可以围绕链码方法、事件、跨链码调用来设计流程推进。
- Solidity 合约必须把流程推进压缩成链上函数调用和状态迁移，且要考虑 gas、重入、安全检查和事件日志。
- BPMN 里的消息发送、确认、网关判断、业务规则继续执行，在两端都需要不同的代码生成策略。

#### 2.3 外部规则与外部服务接入方式不同

- Fabric 侧更容易通过链码调用或链下服务协作接入 DMN/Oracle。
- Geth 侧无法直接做任意链下调用，通常需要 Oracle/回调/异步请求模型。
- 所以同一个 `businessrule` 或 `oracletask`，在 Solidity 中通常要被拆成“请求”和“继续执行”两段式逻辑。

#### 2.4 数据模型与类型系统不同

- Fabric Go 链码的数据结构更灵活，字符串、结构体、映射和 JSON 序列化都比较自然。
- Solidity 的类型系统更严格，动态数据、字符串、映射、数组和返回值处理都更受限制。
- BPMN/DMN 中抽取出的全局变量、消息 schema、决策输入输出，落到 Solidity 时需要更强的类型收敛与编码约束。

### 3. 对生成器带来的直接影响

因此，系统不能只做“一个 DSL，对应两套模板”的浅层适配，而必须在中间层解决这些问题：

- 先把 BPMN/DMN 语义收敛为平台无关的 **B2CDSL**。
- 再在 Fabric 渲染阶段注入联盟链身份、链码调用、FFI 和事件语义。
- 再在 Geth 渲染阶段注入 EVM 状态机、地址权限、异步 DMN/Oracle 调用和 ABI 约束。

也就是说，**最大挑战是如何让同一份中间语义在两种异构区块链执行模型下都保持语义等价**。

### 4. 一句话总结

Fabric 生成与 Geth 生成之间最大的差异，是：

**Fabric 面向“联盟链业务链码执行环境”，Geth 面向“EVM 合约状态机执行环境”；两者在身份、调用、状态推进、外部依赖接入和数据约束上都不同，因此跨平台代码生成的核心难点是语义保持，而不是语法转换。**
