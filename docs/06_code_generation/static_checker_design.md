# 4.7 Static Checker Design

## 1. 目标

静态检查器的目标不是重新执行流程，而是利用 DSL 到代码的可追踪信息，检查生成结果是否保持了源 DSL 的关键语义。

## 2. 输入

静态检查器至少需要三类输入：

- B2CDSL 模型；
- 生成后的 Go 链码或 Solidity 合约；
- DSL 到代码的 traceability 表。

## 3. 检查内容

### 3.1 结构完整性

检查每个 DSL 元素是否都在目标代码中有对应实现：

- 每个 `message` 是否生成 `Send/Complete`；
- 每个 `gateway` 是否生成对应处理函数；
- 每个 `event` 是否生成对应方法；
- 每个 `businessrule` 是否生成规则处理逻辑。

### 3.2 身份约束一致性

检查：

- DSL `participant` 是否映射为 Go 的 MSP 校验；
- DSL `participant` 是否映射为 Solidity 的地址/角色校验。

### 3.3 状态推进一致性

检查：

- `enable` 是否对应目标元素进入可执行状态；
- `message completed` 是否对应后继函数中的状态推进；
- `parallel join` 是否对应多前驱完成检查；
- `businessrule done` 是否对应下游启用逻辑。

### 3.4 决策绑定一致性

检查：

- `businessrule` 是否带有 DMN 资源名和 decision id；
- 输入输出映射变量是否在代码中出现；
- 决策输出变量是否真正参与后续 gateway 分支判断。

## 4. 依赖的 traceability 信息

检查器可利用以下规则：

- 元素 ID 直接出现在函数名；
- 事件名直接出现在 `SetEvent` 或 Solidity `event emit` 中；
- 全局变量名直接出现在实例状态字段中；
- 规则节点保留 `*_Continue` 这样的后缀约定。

## 5. 典型检查流程

1. 解析 DSL，建立元素索引。
2. 解析生成代码中的函数名、事件名、状态字段名。
3. 根据命名规则建立映射关系。
4. 对照 flow 规则检查后继状态更新是否存在。
5. 输出缺失项、不一致项和潜在语义回归项。

## 6. 当前实现下最适合做的静态检查

基于当前代码生成器，最现实、最稳定的检查包括：

- 命名级可追踪检查；
- 结构覆盖检查；
- 关键状态推进检查；
- 决策输入输出变量覆盖检查。

相比之下，完全自动化验证任意运行路径是否等价，还需要更强的中间语义模型。

## 7. 论文中可直接使用的结论

- `B2CDSL` 通过稳定命名把 DSL 与目标代码连接起来；
- 这种 traceability 支持静态检查器在不运行链码/合约的前提下完成结构与语义一致性分析；
- 因而，代码生成不只是“模板展开”，而是具备可验证性的模型驱动转换过程。
