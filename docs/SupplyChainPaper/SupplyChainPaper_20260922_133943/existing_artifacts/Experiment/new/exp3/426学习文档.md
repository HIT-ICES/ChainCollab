# 426 学习文档：Exp3 DSL、Solidity 与 Fabric 执行轨迹对齐

## 一句话目标

实验三要验证：同一个业务流程、同一条执行路径，在 **DSL 模拟执行器**、**Geth/Solidity 自动执行脚本** 和 **Fabric 自动执行脚本** 中是否表现出一致的流程推进轨迹。

当前实验的执行顺序是两阶段的：先跑 **Geth/Solidity vs DSL** 主流水线，得到 `dsl.normalized.json`、`solidity.normalized.json` 和 `comparison.json`；再单独执行 Fabric 回放，把 Fabric 的执行结果归一化后接入已有输出，补齐 `DSL vs Fabric` 和 `Solidity vs Fabric` 两组对比。`SupplyChainPaper` 的典型输入与输出包括：

- BPMN 输入案例：`/root/code/ChainCollab/Experiment/BPMNwithDMNcase/SupplyChainPaper.bpmn`
- DSL/B2C 语义源：`/root/code/ChainCollab/Experiment/new/exp2_semantic_verification/results/cases/SupplyChainPaper/dsl.b2c`
- 平台无关路径：`/root/code/ChainCollab/Experiment/new/exp3/cases/SupplyChainPaper/paths/SupplyChainPaper_auto_path_001/logical_path.json`
- DSL normalized 输出：`/root/code/ChainCollab/Experiment/new/exp3/outputs/SupplyChainPaper/paths/SupplyChainPaper_auto_path_001/normalized/dsl.normalized.json`
- Solidity normalized 输出：`/root/code/ChainCollab/Experiment/new/exp3/outputs/SupplyChainPaper/paths/SupplyChainPaper_auto_path_001/normalized/solidity.normalized.json`
- Fabric normalized 输出：`/root/code/ChainCollab/Experiment/new/exp3/outputs/SupplyChainPaper/paths/SupplyChainPaper_auto_path_001/normalized/fabric.normalized.json`
- 三方对比输出：`comparison.json`、`comparison.dsl_fabric.json`、`comparison.solidity_fabric.json`

## 总体流程

完整链路是：

```text
执行路径输入
  -> DSL 模拟执行
  -> Solidity/Geth 自动执行
  -> 归一化 DSL 与 Solidity
  -> 比较 DSL vs Solidity
  -> Fabric 自动执行
  -> 归一化 Fabric 并接入已有 DSL/Solidity normalized trace
  -> 补齐 DSL vs Fabric、Solidity vs Fabric 对比
```

这几个阶段是独立的：

- DSL 模拟执行不会调用链。
- Solidity 自动执行不会调用 DSL 模拟器。
- Fabric 自动执行不会调用 DSL 模拟器。
- 归一化脚本只做格式转换，不改变原始执行结果。
- 对比脚本/命令只读取 normalized JSON，不反向影响执行。

所以当前实验不是一次命令同时跑三条链路，而是：

```text
第一阶段: run_case_pipeline.py
  跑 DSL + Geth/Solidity，并生成 DSL vs Solidity 对比

第二阶段: run_fabric_case_paths.py
  跑 Fabric，并基于第一阶段已经存在的 normalized 结果补齐三方对比
```

## 1. 执行路径输入

现在采用一份平台无关的统一路径源：

```text
/root/code/ChainCollab/Experiment/new/exp3/cases/<CaseName>/paths/<PathName>/logical_path.json
```

以后优先维护这个文件。它描述的是“业务上这一条路径应该经过哪些元素”，同时允许携带两类执行所需字段：

- `payload`：message / gateway / event / business rule request 使用。
- `outputs`：DSL 模拟 business rule 输出使用。
- `continue_payload`：Solidity 和 Fabric business rule continue 使用。

从这份 logical path 派生 DSL/Solidity 平台输入的脚本是：

```text
/root/code/ChainCollab/Experiment/new/exp3/scripts/materialize_logical_path.py
```

生成命令：

```bash
cd /root/code/ChainCollab
/root/code/ChainCollab/src/newTranslator/.venv/bin/python \
  /root/code/ChainCollab/Experiment/new/exp3/scripts/materialize_logical_path.py \
  --logical-path /root/code/ChainCollab/Experiment/new/exp3/cases/SupplyChainPaper/paths/paper_very_low_delivery_path/logical_path.json \
  --model /root/code/ChainCollab/Experiment/new/exp2_semantic_verification/results/cases/SupplyChainPaper/dsl.b2c \
  --dsl-case-output /root/code/ChainCollab/Experiment/new/exp3/dsl/SupplyChainPaper/paths/paper_very_low_delivery_path/case.json \
  --solidity-sequence-output /root/code/ChainCollab/Experiment/new/exp3/solidity/SupplyChainPaper/paths/paper_very_low_delivery_path/execution_sequence.json
```

这个命令的作用不是“直接运行实验”，而是围绕同一份平台无关的 `logical_path.json` 准备各执行线要使用的路径输入：

- `case.json`
  - 给 DSL 模拟器使用的路径输入
- `execution_sequence.json`
  - 给 Solidity 自动执行器使用的步骤序列输入
- `logical_path.json`
  - Fabric 自动执行器直接使用的路径输入，通过 `replay_fabric_instance.py --sequence-file` 或 `run_fabric_case_paths.py --paths-dir` 传入

也就是说，这一步准备的是“平台输入”，不是最终轨迹结果、对比结果或报告。DSL 和 Solidity 会额外落出各自的派生文件；Fabric 复用原始 `logical_path.json`，不再额外生成一份 Fabric 专用路径文件。

可以把它理解成：

```text
logical_path.json
  -> materialize_logical_path.py
  -> DSL case.json
  -> Solidity execution_sequence.json
  -> Fabric replay 直接作为 --sequence-file
```

其中 DSL 和 Solidity 两份输出并不完全相同，因为两个平台的执行口径不同：

- DSL `case.json`
  - 会省略 DSL 模拟器会自动 bootstrap 的 `start event`
  - 会省略 DSL 语义里自动完成的 `parallel join gateway`
- Solidity `execution_sequence.json`
  - 会保留这些步骤，因为链上执行需要显式 invoke

因此，`materialize_logical_path.py` 做的不是简单复制，而是把同一条 logical path 翻译成 DSL 和 Solidity 各自可执行的输入格式。Fabric 侧当前不需要额外派生文件，`replay_fabric_instance.py` 直接通过 `--sequence-file` 读取同一份 `logical_path.json`；配置文件里的 `execution_sequence_file` 只作为默认值兜底。

生成后，DSL 模拟执行使用：

```text
/root/code/ChainCollab/Experiment/new/exp3/dsl/SupplyChainPaper/paths/paper_very_low_delivery_path/case.json
```

Solidity 自动执行使用：

```text
/root/code/ChainCollab/Experiment/new/exp3/solidity/SupplyChainPaper/paths/paper_very_low_delivery_path/execution_sequence.json
```

也就是说，现在不是手工维护多份路径，而是：

```text
logical_path.json
  -> materialize_logical_path.py
  -> dsl/SupplyChainPaper/paths/paper_very_low_delivery_path/case.json
  -> solidity/SupplyChainPaper/paths/paper_very_low_delivery_path/execution_sequence.json
  -> fabric replay 直接读取 logical_path.json
```

logical path 中的单步示例：

```json
{
  "type": "message",
  "element": "Message_1wswgqu",
  "payload": {
    "orderDetails": "Bulk order for finished goods"
  }
}
```

当前完整逻辑路径是：

```text
Event_06sexe6
Message_1wswgqu
Message_1ajdm9l
Gateway_0onpe6x
Message_0cba4t6
Message_0pm90nx
Gateway_1fbifca
Message_0rwz1km
Message_0hpha6h
Message_1io2g9u
Activity_0rm8bkp
Gateway_0ep8cuh
Message_0d2xte5
Gateway_1cr0nma
Message_04wmlqe
Message_196q1fj
Event_13pbqdz
```

派生时有一个重要平台差异：DSL 模拟器会自动 bootstrap start event，并且 parallel join 在 DSL 里是自动完成的。因此 materialize 后的 DSL case 不显式写 `Event_06sexe6` 和 `Gateway_1fbifca`；Solidity execution sequence 会保留它们，因为链上执行需要显式 invoke。归一化时会把 DSL 自动完成的 parallel join 补齐成可对比的 logical step。

如果不想手工写路径，可以用自动路径生成脚本：

```text
/root/code/ChainCollab/Experiment/new/exp3/scripts/generate_dsl_paths.py
```

它的作用是：

- 从 B2C/DSL 模型自动分析“下一步哪些元素可执行”
- 递归展开不同执行分支
- 生成一批平台无关的合法执行路径
- 供后续流程继续派生 `logical_path.json`、DSL `case.json`、Solidity `execution_sequence.json`，并作为 Fabric replay 的 `--sequence-file`

也就是说，这一步做的不是链上执行，而是**先在 DSL 参考语义层把路径空间展开出来**，作为后续三方回放的共同输入来源。

它从 B2C/DSL 模型出发，使用 DSL 模拟器语义递归枚举当前 `READY` 元素，自动生成 **bounded executable paths**。这里的 `bounded` 很重要，表示它不是无限意义上的“所有路径证明”，而是在当前边界和抽象下做路径枚举。对 `SupplyChainPaper` 的运行命令：

```bash
cd /root/code/ChainCollab
/root/code/ChainCollab/src/newTranslator/.venv/bin/python \
  /root/code/ChainCollab/Experiment/new/exp3/scripts/generate_dsl_paths.py \
  --model /root/code/ChainCollab/Experiment/new/exp2_semantic_verification/results/cases/SupplyChainPaper/dsl.b2c \
  --case-name SupplyChainPaper \
  --output /root/code/ChainCollab/Experiment/new/exp3/cases/SupplyChainPaper/generated_paths.json \
  --max-depth 64 \
  --max-paths 1000
```

当前 `SupplyChainPaper` 会生成 8 条可执行路径：

- parallel split 后两个 message 的执行顺序有 2 种。
- business rule 的 `FinalPriority` 分支有 4 种：`Low`、`High`、`Medium`、`VeryLow`。
- 因此总数是 `2 * 4 = 8`。

输出文件：

```text
/root/code/ChainCollab/Experiment/new/exp3/cases/SupplyChainPaper/generated_paths.json
```

需要注意，这里的“自动枚举路径”有几个边界：

- 它枚举的是**合法可执行路径**，不是非法/拒绝路径全集。
- 它受 `--max-depth` 和 `--max-paths` 限制，因此更准确的说法是“有界路径枚举”。
- 如果模型里存在循环，当前实现不会无限展开，而是通过状态重复截断和深度上界停止继续搜索。
- `gateway` 的 `compare/else` 分支可参与枚举；`expression` 型分支当前模拟器不求值，因此不会被当作可命中分支。

因此，文档里更严谨的表述应是：

> `generate_dsl_paths.py` 会根据 DSL 模拟器语义，自动枚举当前模型在给定边界下的可执行路径，并把这些路径作为 exp3 后续平台对照执行的统一来源。

## 4. Fabric 自动执行

Fabric 是第二阶段接入的执行线。它不负责重新生成 DSL 或 Solidity 结果，而是在第一阶段已经完成 `Geth/Solidity vs DSL` 后，读取同一批 `logical_path.json` 逐条执行 Fabric，并把结果对齐到已有的 `dsl.normalized.json` 和 `solidity.normalized.json` 上。

Fabric 入口脚本分两层：

```text
/root/code/ChainCollab/Experiment/new/exp3/scripts/replay_fabric_instance.py
/root/code/ChainCollab/Experiment/new/exp3/scripts/run_fabric_case_paths.py
```

配置文件：

```text
/root/code/ChainCollab/Experiment/new/exp3/fabric/fabric_replay_config.from_frontend_param.json
```

配置里重要内容：

- `firefly_core_url`：默认 FireFly Core API 地址。
- `event_core_urls`：多 Core 环境下用于查询事件状态的候选地址。
- `namespace`、`api_name`、`chaincode`：Fabric API 和链码定位信息。
- `default_signer`、`participant_signers`、`signer_overrides`：Fabric 调用 signer。
- `create_instance_params`：Fabric createInstance 参数，包括 participant 和 DMN 配置。
- `execution_sequence_file`：默认路径文件；批量跑案例时会被命令行 `--sequence-file` 覆盖。

单条路径执行时，`replay_fabric_instance.py` 会：

1. 读取配置和 `logical_path.json`
2. 创建 Fabric 流程实例
3. 等待目标元素进入可执行状态
4. 逐步调用 Fabric FireFly API
5. 记录每一步 `payload`、`response`、`snapshot_after`
6. 输出 `fabric/<CaseName>/paths/<PathName>/replays/replay_*.json`
7. 默认自动调用 `compare_fabric_replay.py` 做归一化和对比

批量跑某个案例时，使用：

```bash
cd /root/code/ChainCollab/Experiment/new/exp3
python3 scripts/run_fabric_case_paths.py \
  --config fabric/fabric_replay_config.from_frontend_param.json \
  --paths-dir cases/SupplyChainPaper/paths
```

这个命令会自动发现：

```text
cases/SupplyChainPaper/paths/*/logical_path.json
```

然后依次调用 `replay_fabric_instance.py`，每条路径的 Fabric 中间产物会放在：

```text
fabric/SupplyChainPaper/paths/<PathName>/replays/
```

批量汇总会放在：

```text
fabric/SupplyChainPaper/batch/fabric_batch_<timestamp>.json
fabric/SupplyChainPaper/batch/fabric_batch_<timestamp>.md
```

Fabric 原始 replay 的关键字段：

- `instance_id`：Fabric 流程实例 ID。
- `steps`：每次 Fabric invoke 后的执行记录。
- `element_type`、`element_id`、`method`：本步执行的逻辑元素和链码方法。
- `payload`：本次调用输入。
- `response`：FireFly invoke 响应。
- `snapshot_after`：本步执行后的 Fabric 状态快照。
- `final_snapshot`：最终 Fabric 状态快照。

## 5. 轨迹归一化

归一化脚本：

```text
/root/code/ChainCollab/Experiment/new/exp3/scripts/normalize_traces.py
/root/code/ChainCollab/Experiment/new/exp3/scripts/compare_fabric_replay.py
```

这个脚本只做格式转换，不改原始执行含义。

它做的事：

- 把 DSL 原始 trace 转成统一字段。
- 把 Solidity 状态数组还原成 `{element_id: state}`。
- 把 Solidity 的 business rule request + continue 折叠成一个 logical step。
- 把 Fabric 状态数组还原成 `{element_id: state}`。
- 把 Fabric 的 business rule request + continue 折叠成一个 logical step。
- 把 DSL 自动完成的 parallel join 补成 `synthetic_parallel_join` step。
- 保留 `raw_steps`，方便回查原始执行细节。

## 7. 两个特殊对齐规则

### 7.1 Business rule 折叠

Solidity 和 Fabric 原始执行中，business rule 都可能拆成 request 和 continue 两个调用：

```text
Activity_0rm8bkp
Activity_0rm8bkp_Continue
```

normalized 后折叠成：

```text
Activity_0rm8bkp
```

原因：DSL 模拟器把 business rule 看作一个逻辑步骤，而链上实现需要 request 和 continue 两次调用。

### 7.2 Parallel join 补齐

DSL 原始模拟中，`Gateway_1fbifca` 是 parallel join，满足两个前置消息完成后自动完成：

```text
Message_0cba4t6 DONE
Message_0pm90nx DONE
=> Gateway_1fbifca DONE
=> Message_0rwz1km READY
```

Solidity 和 Fabric 中需要显式执行：

```text
Gateway_1fbifca
```

所以 normalized DSL trace 里会补一条：

```text
phase = synthetic_parallel_join
trigger.element = Gateway_1fbifca
```

这样三条执行线的 logical steps 才能逐步对齐。

## 11. 读项目时的心智模型

你可以把当前实验看成三层：

第一层是执行：

- DSL 模拟器执行 DSL 参考语义。
- Solidity 脚本执行真实链上合约。
- Fabric 脚本执行真实 Fabric 链码。

第二层是记录：

- DSL 输出自己的原始 trace。
- Solidity 输出自己的链上 replay JSON。
- Fabric 输出自己的链码 replay JSON。

第三层是对齐：

- normalized trace 把三个不同世界的输出翻译成同一种比较语言。
- 后续对比只看 normalized trace。

最重要的一点：归一化不是执行，不改变事实；它只是把事实重新排版成可比较的结构。

## 12. Chainlink LINK 余额注意事项

链上执行到 business rule / DMN 节点时，会通过 `dmnLiteAddress` 对应的 `MyChainlinkRequesterDMN_Lite` 合约发起 Chainlink 请求。每次请求会消耗 LINK，目前部署里的 fee 是 `0.1 LINK`。

如果 Solidity replay 在业务规则节点报错：

```text
ERC20: transfer amount exceeds balance
```

优先检查 `dmnLiteAddress` 的 LINK 余额。这通常不是 BPMN/DMN 路径参数问题，而是请求合约没有足够 LINK 支付 oracle 请求。

当前环境可以用下面方式补充 LINK：

```bash
cp /root/code/ChainCollab/src/runtime/deployment/deployment.json \
  /root/code/ChainCollab/src/oracle/CHAINLINK/deployment/deployment.json

cd /root/code/ChainCollab/src/oracle/CHAINLINK
RPC_URL=http://localhost:9603 node scripts/fund-contract.js
```

连续跑多条路径前，建议先确认余额足够；否则前几条路径成功后，后面的路径可能因为 LINK 被消耗完而失败。
