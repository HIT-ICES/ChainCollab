# 3.5 Blockchain-oriented Modeling Constraints

## 1. 为什么这不是普通 BPMN / DMN 建模

`newTranslator` 的目标不是只做流程建模，而是把流程和决策进一步生成成：

- Hyperledger Fabric 的 Go 链码
- Geth/EVM 的 Solidity 合约

因此，这里的建模天然面向区块链执行环境，必须额外满足：

- 身份可映射
- 消息可映射
- 状态可映射
- 决策结果可落链
- 外部规则调用可约束

## 2. 参与方如何映射为链上身份

### 2.1 BPMN / DSL 侧

- BPMN：`participant`
- DSL：`participant { msp ... x509 ... attributes ... }`

### 2.2 Fabric 侧

参与方会映射为：

- `MSP`
- `X.509`
- 扩展属性

这使得链码能够做：

- 组织身份校验
- 调用者角色检查
- 多企业授权边界控制

### 2.3 Solidity / Geth 侧

参与方会映射为：

- 枚举化的参与方标识
- 地址或外部身份注册表约束

这意味着建模时必须清楚表达“谁是谁”，否则权限控制无法生成。

## 3. 消息如何映射为交易调用

### 3.1 建模侧

- BPMN：`message` + `messageFlow` + `choreographyTask`
- DSL：`message ... from ... to ...`

### 3.2 生成侧

消息会进一步映射为：

- Fabric：链码方法调用、消息完成方法、FFI 方法
- Solidity：合约函数调用、状态切换、事件记录

因此建模时必须明确：

- 谁发
- 谁收
- 传什么数据

否则无法生成稳定的交易接口。

## 4. 流程状态如何映射为链上状态

在 `newTranslator` 中，流程元素会统一抽象成状态机元素。

DSL 层的核心状态有：

- `INACTIVE`
- `READY`
- `PENDING_CONFIRMATION`
- `DONE`

这些状态在生成代码时会映射为：

- Fabric 中实例对象的状态字段
- Solidity 合约中的枚举/存储状态

所以建模的本质不是“画图”，而是定义：

- 哪些节点何时启用
- 哪些节点何时完成
- 哪些节点会推动后续状态转移

## 5. 决策结果如何记录

决策结果不会只停留在 DMN 表中，而必须落入流程可见状态。

当前路径是：

1. `BusinessRuleTask` 定义输入输出
2. `output mapping` 把规则结果写到 DSL `globals`
3. 后续网关或动作读取这些 `globals`
4. 生成代码把这些变量持久化为链上状态

也就是说，决策结果本质上被建模为：

- **链上可读的全局状态变量**

## 6. 外部 DMN 调用如何约束输入输出

无论是 Fabric 还是 Solidity，决策调用都不能是“随便丢给外部规则引擎”。

必须约束：

- 输入变量来源明确
- 输出变量回写明确
- 类型匹配明确

这就是为什么系统要求：

- `input mapping`
- `output mapping`
- 全局变量类型

都要建模清楚。

如果没有这些约束，外部 DMN 调用就无法稳定生成代码。

## 7. 建模时必须遵守的规则

从区块链代码生成角度，至少要遵守以下规则：

- 参与方必须明确、可区分
- 消息必须明确发送方和接收方
- 流程必须有唯一入口
- 分支条件必须可判定、可类型检查
- 决策输入输出必须映射到全局变量
- 并行等待源必须明确
- 同一动作不能同时启用和禁用同一节点
- 类型必须与目标代码生成兼容

这些约束在现有系统中，已经分别体现在：

- DSL 语法
- OCL 校验规则
- 代码生成器实现边界

## 8. 这类约束为什么重要

如果只是普通 BPMN / DMN 工具，很多图形化自由度可以接受。

但在 `newTranslator` 中，模型必须进一步满足：

- 可解析
- 可验证
- 可翻译
- 可执行

否则就无法自动生成区块链程序。

## 9. 一句话总结

`newTranslator` 的建模之所以是“面向区块链”的，是因为它要求流程和决策模型不仅要有业务意义，还必须能被确定性地映射为：

- 链上身份
- 交易调用
- 状态机
- 决策结果存储
- 可验证的输入输出边界
