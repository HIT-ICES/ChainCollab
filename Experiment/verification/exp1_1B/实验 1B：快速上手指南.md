# 实验 1B：快速上手指南

本文档面向刚接手实验 1B 的人，目标是在最短时间内理解这个实验项目“做什么、怎么跑、看哪里、结果说明什么”。

如果你要看完整实验设计，请读同级文档：

```text
实验 1B：BPMN→DSL 源目标结构一致性验证详细实验方案.md
```

本文档只做快速入门。

## 1. 一句话理解实验 1B

实验 1B 验证的是：

```text
BPMN 源模型经过 newTranslator 翻译成 B2C DSL 后，
源模型中的关键结构是否在 DSL 中被完整、正确、可追踪地保留下来。
```

它不是运行时实验，不检查 Fabric / Geth，也不检查 Go / Solidity 代码。

它只检查结构：

```text
BPMN 有哪些元素？
DSL 中有没有对应元素？
类型是否对应？
关键属性是否保留？
结构关系是否保留？
DSL 中有没有无 BPMN 来源的关键元素？
```

## 2. 这个实验项目分两部分

### 2.1 主体实验

主体实验位于：

```text
/root/code/ChainCollab/Experiment/new/exp1_1B
```

主体实验做 BPMN->DSL 的结构一致性检查，核心检查项是 C1-C5：

```text
C1 element_coverage
  BPMN 应转换元素是否都能在 DSL 中找到对应结构。

C2 type_consistency
  BPMN 元素类型是否映射为正确的 DSL 类型。

C3 attribute_preservation
  BPMN 关键属性是否在 DSL 中保持。

C4 relation_preservation
  BPMN 结构关系是否在 DSL 中保留。

C5 target_traceability
  DSL 关键业务元素是否都有 BPMN 来源或派生来源。
```

### 2.2 附加实验

附加实验位于：

```text
/root/code/ChainCollab/Experiment/new/exp1_1B/Addition
```

附加实验检查实验三的 `logical_path.json`：

```text
实验三 logical_path 中的每个 step.element，
是否存在于 DSL-TAG，
并且是否能通过 bpmn_dsl_trace.json 追溯到 BPMN 来源。
```

它只证明实验三路径具有 BPMN 结构来源，不证明路径执行语义正确。

## 4. 最重要的文件

### 4.1 映射契约

```text
contracts/default_mapping_contract.json
```

它定义 BPMN 和 DSL 的对应规则。

例如：

```text
bpmn:participant -> dsl:participant
bpmn:message -> dsl:message
bpmn:startEvent -> dsl:event
bpmn:businessRuleTask -> dsl:businessrule
```

契约定义了 13 条 element_rules 和 9 条 relation_rules，全部已在 `check_structure_consistency.py` 中实现检查：

```text
13 条 element_rules：
  - 11 条 direct 映射（participant/message/event/gateway/businessrule/oracletask）
  - 3 条 derived global 映射（messageProperty/businessRuleParameter/sequenceConditionVariable → global）

9 条 relation_rules：
  - 4 条 required=true（messageFlow sender/receiver、startEvent start_enables、
    choreographyTask message ordering、messageFlow endpoints）
  - 5 条 required=false（parallelGateway join、eventBasedGateway disable+enable、
    exclusiveGateway condition gateway_branch、businessRuleTask/oracleTask done flow、
    通用 sequenceFlow enable fallback）
```

需要特别理解：

```text
messageFlow 在 DSL 中不是独立业务节点，
而是体现为 message 的 sender / receiver。

choreographyTask 在 DSL 中不是独立业务节点，
而是展开为 message 顺序和 enable 关系。

global 从 BPMN documentation、参数或条件变量中派生，
检查脚本会验证 public_the_name 名称和类型（含布尔/整数/浮点/字符串推断）。
```

### 4.2 TAG 格式定义

```text
schemas/tag_format.schema.json
```

TAG 是 Typed Attributed Graph，即类型化属性图。

简单理解：

```text
nodes = 元素
edges = 关系
attrs = 元素或关系的关键属性
```

BPMN 和 DSL 都先被抽取成 TAG，再进行对比。

## 5. 主体实验是怎么跑的

主体实验流程：

```text
BPMN 源文件
  ↓ 调用 newTranslator
B2C DSL 文件

BPMN 源文件
  ↓ extract_bpmn_structure.py
BPMN-TAG

B2C DSL 文件
  ↓ extract_dsl_structure.py
DSL-TAG

BPMN-TAG + DSL-TAG + default_mapping_contract.json
  ↓ build_bpmn_dsl_trace.py
bpmn_dsl_trace.json

BPMN-TAG + DSL-TAG + bpmn_dsl_trace.json
  ↓ check_structure_consistency.py
结构一致性报告
```

`check_structure_consistency.py` 一次性执行 C1-C5 全部检查：

```text
C1 元素覆盖：BPMN direct 元素 + choreographyTask expansion
C2 类型一致性：11 种 direct 类型的映射正确性
C3 属性保持：id/name + 类型专属属性（participant multiplicity、message schema、
   event initialState、gateway gatewayType、businessrule dmnResource/decisionID/paramMapping、
   oracletask oracleType/dataSource/computeScript/outputMappings）+
   global 派生变量（public_the_name 名称 + 类型推断）
C4 关系保持：9 条关系规则全部检查
C5 目标可追踪性：6 类关键 DSL 元素均有 BPMN 来源
```

注意：

```text
default_mapping_contract.json 是共用规则；
bpmn_dsl_trace.json 是每个 case 单独生成的追溯结果。
```

例如：

```text
cases/SupplyChainPaper/trace/bpmn_dsl_trace.json
cases/Purchase/trace/bpmn_dsl_trace.json
cases/Hotel_Booking/trace/bpmn_dsl_trace.json
```

它们不是同一个文件。

## 9. 怎么理解 trace

`bpmn_dsl_trace.json` 是每个 case 的源目标追溯关系文件。

它由以下三个输入生成：

```text
bpmn_tag.json
dsl_tag.json
default_mapping_contract.json
```

它的作用是回答：

```text
BPMN 中的某个元素，对应 DSL 中的哪个元素？
BPMN 中的某个 messageFlow，对应 DSL message 的哪些 sender/receiver 关系？
DSL global 是从 BPMN 的哪些 documentation / 参数 / 条件派生出来的？
  （C3 会检查其 public_the_name 名称和类型是否一致）
choreographyTask 虽然没有 DSL 同名节点，它由哪些 message / enable 结构表示？
businessRuleTask 的 inputs/outputs 在 DSL 中对应哪些 paramMapping？
  （C3 会检查 dmnnParam 名和 globalRef 是否一致）
oracletask 的 oracleType / dataSource / computeScript 在 DSL 中是否保持？
```

后续 C1-C5 检查会使用 trace，但不只看 trace。

三类文件的关系：

```text
bpmn_tag.json
  提供 BPMN 侧事实。

dsl_tag.json
  提供 DSL 侧事实。

bpmn_dsl_trace.json
  提供二者之间的对应关系。
```

一致性检查在这三者基础上判断：

```text
元素是否覆盖；
类型是否正确；
属性是否保留；
关系是否保留；
DSL 目标是否可追溯。
```

## 10. 新人最常见的问题

### 10.1 `bpmn_dsl_trace.json` 是所有 case 共用的吗？

不是。

共用的是：

```text
contracts/default_mapping_contract.json
schemas/tag_format.schema.json
scripts/*.py
```

每个 case 独立生成：

```text
cases/<CaseName>/bpmn/bpmn_tag.json
cases/<CaseName>/dsl/dsl_tag.json
cases/<CaseName>/trace/bpmn_dsl_trace.json
cases/<CaseName>/reports/*.json
```

### 10.2 trace 已经对齐了，为什么还要后续检查？

因为 trace 只说明”谁对应谁”，后续检查判断”对应是否完整、正确、有无遗漏”。

例如：

```text
trace 找到了 Message_A -> Message_A；

C2 还要检查类型是不是 bpmn:message -> dsl:message；
C3 还要检查 schema 是否一致；
C4 还要检查 sender / receiver 关系是否正确；
C5 还要检查 DSL 中有没有多出来的无来源关键元素。
```

再如：

```text
trace 找到了 Derive_Amount -> Amount（global 派生）；

C3 还要检查 Amount 在 DSL 中的名称是否为 public_the_name 规范化结果；
C3 还要检查推导出的类型（boolean/integer/float/string）是否与 DSL 声明一致。
```

又如：

```text
trace 找到了 BusinessRule_A -> BusinessRule_A；

C3 还要检查 input/output paramMapping 中 dmnParam 名和 globalRef 是否正确；
C4 还要检查 businessrule done 后的 enable 后继关系（BusinessRuleSequence2RuleFlow）。
```

### 10.3 附加实验算不算 1B 主体？

不算。

1B 主体是 C1-C5 结构一致性检查。

附加实验只是 1B 与实验三之间的衔接检查：

```text
实验三路径 step 是否具有 BPMN 来源？
```

它不影响 1B 主体结构一致性结论。

### 10.4 这个实验是否修改 newTranslator？

不修改。

1B 脚本只调用：

```text
/root/code/ChainCollab/src/newTranslator/generator/bpmn_to_dsl.py
```

来生成 B2C DSL。
